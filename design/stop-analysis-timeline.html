What is decided

The collapsed lane answers one question

A group lane shows only the intervals where the line itself was down — the union of its children’s line-impacting stops. A machine that stopped without taking production down (a weigher on standby, a spare erector) contributes nothing to the group bar and only appears once you expand. So expanding always reveals more, never less, and the collapsed view stays a clean read of availability.

Colour is the plant’s existing vocabulary, not a new one

Bars reuse HmiStateColors exactly as the mimic assets do, so an operator does not learn a second colour language. Lane background is the neutral container gray — running time is deliberately unpainted, per ISA-101. Only fault red is saturated.

Short stops stay visible

Over an eight-hour window a 40-second stop is a fifth of a pixel. Bars clamp to a 3 px minimum and grow a hairline tick above and below when they are at the clamp, so a burst of micro-stops reads as a comb rather than disappearing. This is what makes the timeline useful for chronic small stops, which is where most availability actually goes.

Not-scheduled is not downtime

The hatched band is unscheduled time (the 12:00 break). It is excluded from both the downtime totals and the availability figure, so the numbers in the label column mean what a production manager expects them to mean.

The table answers “what should I fix”, the timeline answers “what happened”

Switch to Table and you get a Pareto of the same window: rank by total lost time to find what is expensive, or click Stops to rank by frequency and find what is chronic. These give different answers, and the gap between them is usually the interesting part — one 40-minute seal fault costs the same as eighty 30-second micro-stops, but you fix them in completely different ways. The share column carries a cumulative marker so the 80/20 point is visible without doing arithmetic.

Four rollups: Machine & cause (the actionable pair — “Multivac, blocked”), Machine, Cause, and Every stop as a raw chronological log. The table always reflects the visible time window and the reason filter, so panning the timeline re-ranks it. A row is a way back in: click one and it jumps to the timeline with that machine expanded, or centres the event.

It degrades by height, not by width

Dropped on a page the asset can be anything from a 300 px strip to full screen. At strip height it drops the brush, the detail row and the per-row statistics and keeps group lanes only — still a legible “which line is losing time”. Grab the corner handle above and shrink it.

What SVN actually has today

Checked against the live plant key mapping (1556 keys, snapshot 11 Aug 2026) and the collector config, rather than assumed.

The history already exists — and it is not the alarm system

91 drive structs are collected whole, every 5 seconds, with one-year retention — CVS01.CN01.FD01 and its siblings, each carrying p_stat_State, p_stat_Error and p_stat_LastFault. That is a machine state timeline for most of the plant, already accumulating, with no new plumbing.

alarm_history is the opposite story. The live plant’s alarm_man_config is {"alarms":[]} — zero alarms configured — and the station backup has historyToDb: false, so nothing is being written there at all. The 39 alarms in the older backup belong to the previous Line1.Motor1 topology, not this one. The asset must read equipment state, not alarms. The alarm link stays in the design as an enrichment for the detail row — when a fault interval coincides with an activation, name it — but it cannot be the source, or v1 renders an empty timeline.

Grouping is already in the key names

CVS01.CN01.FD01 is system · device · drive, and the whole live namespace is shaped that way (CVS01–03, SPB01–03, BER02/03, STM02/03, Baader1–10). So the tree can be derived from the key convention with an explicit override for the cases it gets wrong, rather than hand-built from nothing.

The resolution floor is 5 seconds

Collection is periodic sampling, so stop edges quantise to ±5 s and anything shorter can fall between samples. The micro-stop comb above still earns its keep — a 20-second stop is four samples — but it only becomes fully honest if those keys move to change-of-value. The collector already supports that: sample_interval_us: null inserts on every subscription update, which for a state enum means one row per transition. That is a per-key config change, not code.

Volume is the real constraint

91 drives × 5 s × one year is on the order of half a billion rows, each holding a whole struct. The asset has to query a bounded window and fold rows into intervals server-side; pulling a shift of raw samples into the widget will not work.

What is still genuinely open

Which stops impact the line?

There is no system-level run bit in the live namespace — CVS01 has no keys of its own, only CN01…CN39 beneath it. So the rollup really must be a union of children, and something has to say which children count. Most likely a per-child flag in the asset config, defaulting to on.

It also decides what the table means. Right now the Pareto ranks machine downtime regardless of line impact, which is why a weigher can sit at the top of the list while the line it belongs to shows 95% availability. That is honest but it is not the same question as “what cost us the most product”. Once the impact flag exists the table should probably offer both — machine downtime and line-impacting downtime — rather than silently picking one.

How does a state value become a reason?

The six reasons above have to be read off p_stat_State and its neighbours. The enum lives in the PLC source (~/Projects/sildarvinnsla), so this is a mapping to be read rather than invented — but starved and blocked in particular may need the PX01 photocells and Jam bits, not just the drive state.
