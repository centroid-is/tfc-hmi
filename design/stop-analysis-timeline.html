Architecture

Three new pieces, and they sit on top of the alarm system rather than beside it. The one thing that is not obvious: the intervals come from two places and have to be unioned, because a row only reaches alarm_history when the alarm clears.

An alarm can be a leaf or the branch itself

A leaf is a diagnosis — film reel empty. But where no diagnosis alarm exists yet, an alarm binds to the branch and is that machine’s signal. Both can be true at once: Multivac has a coarse alarm of its own and finer ones underneath, so anything the fine alarms don’t explain still shows up. Adding a diagnosis later is a new alarm definition, not a restructuring.

Making it fast

The first version of this mockup took 51 ms per pan frame with 45 rows and 62 bars — about 19 fps on a dataset small enough to be a rounding error. It is now 0.2 ms for the same frame with a forced layout included. Four things were wrong, and all four have direct Flutter equivalents.

  • It re-merged every rollup on every frame. A node’s intervals are a pure function of its subtree and the severity filter — panning cannot change them. They are now merged once per filter change and cached. This is the big one.
  • It walked every interval to find the visible ones. The cached lists are sorted and disjoint, so the visible slice is two binary searches, and the window statistics come from a prefix sum in O(log n) instead of a full scan.
  • It tore down and rebuilt the DOM. Bars are created once and re-positioned with transform; gridlines, the hatch and the future dim became one pooled overlay for the whole body instead of eleven elements per row. In Flutter this is the difference between rebuilding a widget subtree and repainting a CustomPainter — and the lanes should be a painter, exactly like the conveyor and elevator assets already are.
  • It read clientWidth inside the write loop, forcing a synchronous layout per row per frame. One measurement is taken before any write.

Two more things keep it flat as data grows: intervals closer together than a pixel are coalesced into one run, so the number of elements touched is bounded by the lane’s width rather than by how much history is loaded; and pan, zoom and the live tick are coalesced to one frame. Honest caveat — this was measured on a few hundred activations. The merge and the coalescing loop are still linear in loaded intervals, which is why the window a query loads matters as much as the drawing.

What the database should do

More than it does now, and it is well placed to — unlike the drive-struct history, an alarm activation already is an interval, one row, no folding of samples required.

  • Insert on activate, update on clear. Today _addToDb only fires from _removeActiveAlarm, and deactivated_at is written as an empty string cast to timestamp. If the row were inserted on activation with a NULL deactivation and updated when it clears, the database could answer “what is standing” too — the two-source union in the diagram above collapses into one query, and the live stream becomes a refresh trigger rather than a second source of truth. Small change to AlarmMan, large simplification everywhere downstream.
  • Index the interval, not the timestamp. Every query here is a range overlap — created_at < :t1 AND (deactivated_at IS NULL OR deactivated_at > :t0) — which is a GiST index on tstzrange(created_at, deactivated_at), not a btree on created_at.
  • Bucket wide windows in SQL. A month view does not need fifty thousand intervals; it needs, per alarm per pixel column, whether anything was standing and the worst severity. That is a width_bucket and a GROUP BY, and it makes the payload constant no matter how wide the window is. Below a threshold the client fetches real intervals and draws them exactly; above it, buckets.
  • The Pareto never needs rows at all. Ranking by standing time and by count is SUM(LEAST(deactivated_at, :t1) - GREATEST(created_at, :t0)) grouped by alarm_uid. The table view should be one query returning a few dozen rows, not a client-side reduction over everything loaded.

The grouping stays client-side on purpose: the tree lives in AlarmConfig.path, which is configuration, not data. Merging pre-bucketed leaves up the tree is cheap — it is merging raw intervals every frame that was expensive, and that is now cached.

How it is built

The tree is the alarm definitions

Every leaf is one alarm, so the leaf is already a diagnosis — not “Multivac stopped” but film reel empty, seal temperature out of band, vacuum not reached. Group rows are the path above it and nest as deep as the definitions do. Expand Line 3 to get Multivac, expand Multivac to get what was actually wrong.

The one thing AlarmConfig is missing for this is the path. It has uid, key, title, description and rules, and nothing that says where an alarm sits. Adding it there rather than in the asset means the hierarchy is a property of the alarm system — the alarm list, the beacon and this timeline all group the same way, and configuring an alarm is the only place you say where it belongs: 

class AlarmConfig {
  final String uid;
  final String? key;
  final String title;
  final String description;
  final List<AlarmRule> rules;

  /// Where this alarm sits in the tree. ["Line 3", "Multivac"]
  final List<String> path;          // new

  /// True: this alarm IS the node at [path] — the branch's own signal.
  /// False: it is a diagnosis leaf underneath that node.
  final bool bindToPath;            // new
}

Colour is severity, straight from AlarmColors

error Solarized red, warning signal yellow, info signal green — the same three the banner, the list cards and the beacon use, and identical in both themes on purpose (ISA-18.2). A group bar takes the worst severity active during that interval, so a line lane goes red the moment any error underneath it stands, and the filter chips are the same severity filter the alarm page already has.

Two things to watch on a floor. Green normally means running, and here a green bar means an info alarm was standing — the lane ground stays neutral grey so nothing reads as “green = healthy”, but if info alarms turn out to be common this is the first thing that will look wrong. And signal yellow is weak against the light theme’s pale surfaces; it is legible, but a warning reads quieter there than it does on dark. Both are inherited from AlarmColors deliberately — fixing them here would mean this asset disagreeing with the banner and the beacon, which is worse.

A live alarm is a bar with no right edge

AlarmMan._addToDb only fires from _removeActiveAlarm, so a row reaches alarm_history when the alarm clears. Read only the table and the one alarm an operator is standing in front of is the one stop missing from the chart. So the timeline unions two sources the way alarmHistoryEntries(history, active) already does for the history list: closed intervals from the database, open intervals from the live activeAlarms() stream. Open ones run to the live edge, pulse, and say ongoing instead of an end time — the clock above is real, so watch one grow.

Short activations stay visible

Over a five-hour window a forty-second alarm is a fifth of a pixel. Bars clamp to a 3 px minimum and grow a hairline tick above and below at the clamp, so a chattering alarm reads as a comb rather than vanishing. That comb is usually the finding.

The table answers “what should I fix”

Rank by total standing time to find what is expensive, or click Count to rank by frequency and find what is chronic — a twenty-minute seal fault and eighty thirty-second film jams cost the same and are fixed completely differently. The share column carries a cumulative marker so the 80/20 point is visible. Rank by alarm, by group, by severity, or list every activation; a row is a way back into the timeline.

Not-scheduled is not downtime

The hatched band is unscheduled time (the 12:00 break), excluded from the totals and from the clear percentage. It degrades by height too: at strip size the asset drops the brush, the detail row and the statistics and keeps top-level groups only.

What this needs from the alarm system

Alarms have to be defined

The live plant’s alarm_man_config was {"alarms":[]} in the 11 Aug prefs export, and the station backup has alarm_man_local_config.historyToDb: false. Neither is an architectural problem — they are settings — but the timeline is exactly as good as the alarm definitions behind it, and it shows nothing until they exist. The 39 alarms in the older backup are all machine-level (“Line 2 Motor 1 Fault”); the diagnosis-level alarms this design is built around — film reel empty, out of strap, blank magazine empty — are new definitions against the PLC tags.

History has to be switched on, in exactly one place

historyToDb is a device-local preference, so if two stations have it on the same activation is written twice, and if none do the timeline only ever shows what is live. There is also no backfill: history starts the day it is enabled.

Which severities count as a stop?

The level ladder is severity, not stopped-versus-running — “air cabinet is off” is an info alarm and may not have stopped anything. The severity chips currently stand in for that decision, which is why the statistics say alarm-clear rather than availability. If a stop is a real distinct property, it belongs next to path on AlarmConfig as a flag, not inferred from the level.
