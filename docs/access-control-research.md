# Users, roles and privileges — what the rest of the industry does

Research note, 2026-08-26. Written before designing anything, so the design
argues with real prior art instead of with intuition.

CentroidX today has **no concept of a user**. There is no login, no identity,
no per-action authorisation and no audit of who wrote what. Every station that
can reach the Postgres config database can open the page editor, remap keys,
edit alarms, and write any OPC UA tag the `StateMan` connection is allowed to
write. That is fine for a single-line install with one trusted crew; it stops
being fine the moment a second shift, a contractor, or a customer audit shows
up.

This note surveys how the established SCADA and MES platforms solve it, pulls
out the patterns they all converged on, and maps those onto the code we
actually have.

---

## 1. Ignition (Inductive Automation)

Ignition is the most instructive because it carries *two* generations of the
model side by side, and the newer one is a deliberate reaction to the limits of
the older one.

**Classic strategy — User Sources and Roles.** A *User Source* is a directory:
internal (stored in the Gateway), a SQL database, or Active Directory. Users
are granted *Roles*, and screens check `hasRole(...)`. AD-backed sources map
domain groups to roles. The house recommendation is to chain Internal as a
fallback behind AD so a break-glass admin can still log in when the domain
controller is unreachable.

**Modern strategy — Identity Providers and Security Levels.** Authentication is
delegated to an OIDC or SAML IdP; authorisation is expressed as a *tree* of
Security Levels rather than a flat role list. Four levels are reserved:

- `Public` — granted to *everyone*, including unauthenticated sessions
- `Authenticated` — child of Public, granted on successful IdP login
- `Authenticated/Roles` — placeholder parent; roles returned by the IdP graft
  themselves underneath by exact name match
- `SecurityZones` — autogenerated placeholder for zone-derived levels

Children inherit their parents, so `Authenticated/Roles/Manager/Shift_Supervisor`
implies everything above it. Custom levels anywhere in the tree are granted by
**Security Level Rules** — expressions over IdP attributes, security zones, tag
values, even time of day. That last part matters: authorisation is *computed*,
not just looked up.

**Security Zones** are orthogonal to identity. A zone is a set of gateways,
machines, hostnames or IP ranges, assigned automatically from the client's
source address with no login involved. "This action is only permitted from a
panel physically on the line" is expressible without any user at all.

**Where permissions attach.** Not one place — several:

- *View permissions*: right-click a Perspective view → configure view
  permissions → tick the required security levels. Denied users get an
  "Access Denied" view, which is itself customisable.
- *Component permissions*: bind `enabled`, `visible` or `display` through
  `isAuthorized(isAll, levels)`. Note the distinction Ignition draws between
  `visible: false` (invisible but still occupies layout space) and
  `display: false` (gone entirely). Which one you pick is a real UX decision —
  a greyed-out control tells the operator "you need someone else"; a vanished
  control tells them "this doesn't exist".
- *Tag permissions*: every tag carries **Read Permissions**, **Read Only**, and
  **Write Permissions** as first-class properties. Authorisation lives on the
  data point, not only on the screen that happens to touch it.
- *Tag editing permissions* (8.0.16+): a separate level check governing who may
  restructure a tag provider — edit UDTs, create/delete tags, call
  `system.tag.configure`, bind bidirectionally. Configuration authority is
  separated from operation authority.

**Session hygiene.** Configurable inactivity logoff, dropping either to a
default operator account or to fully logged out. Auto-login and generic shared
accounts are explicitly discouraged.

## 2. AVEVA System Platform / InTouch OMI

**Authentication modes** are picked per Galaxy: None, OS User Based, OS Group
Based, or Galaxy-internal accounts. OS Group Based is the usual choice — the
plant's AD groups become the Galaxy's security groups, and nobody maintains a
second user list.

**Three separate permission planes**, which is AVEVA's sharpest idea:

- **IDE permissions** — what you may do in the development environment: import
  templates, create or modify object templates, deploy.
- **SMC permissions** — system management and maintenance functions.
- **Runtime permissions** — for each security group, which operations are
  permitted against which Automation Objects at run time.

An engineer who may reconfigure an object template is a *different grant* from
an operator who may command that object, which is a different grant again from
whoever may restart the platform. Collapsing these into one "admin" flag is the
mistake the model exists to prevent.

**Secured and Verified Writes** are the feature most worth stealing. Attributes
can be marked so that a write does not simply happen:

- **Secured Write** — the writing user must re-enter their own credentials at
  the moment of the write. Being logged in is not sufficient; the specific
  action is re-authenticated.
- **Verified Write** — the writer re-authenticates *and* a second, different
  authorised user must also authenticate to approve. Four-eyes at the level of
  a single tag write.

The prompt dialog is customisable, and the event goes to the audit trail with
who, what, when. This is the SCADA-layer ancestor of the MES electronic
signature.

## 3. Rockwell FactoryTalk View

Two mechanisms, layered.

**FactoryTalk Security** holds users and groups in the FactoryTalk Directory
(with Windows-linked accounts as an option) and grants *actions* on nodes of a
resource tree — alarm actions, recipe actions, and so on. Permissions are
**cumulative across group membership**: a user in `ALL USERS` (codes ABCD) and
`ENGINEERING` (codes EFGH) has effective codes ABCDEFGH. There is an "Effective
Permissions" inspector in the tooling, which tells you something — once
inheritance and union are in play, *nobody can work out a user's real rights by
reading the config*, so the platform ships a resolver.

**Runtime security codes A–P** are the older, blunter half: sixteen letters,
each assignable to a display or an object, each grantable to an account. Crude,
but it made per-object authorisation something a technician could configure in
seconds, which is why it survived into SE alongside the richer model.

**Locational security** scopes a grant to a computer or an area — the same idea
as Ignition's security zones, arrived at independently.

## 4. Siemens WinCC / TIA Portal

Authorisations (function rights) are defined in the project, granted to user
groups, and then *attached to individual screen objects*. An object with an
authorisation is inert for a user who lacks it.

**SIMATIC Logon** delegates the whole directory to Windows/AD: the WinCC group
names must match the Windows domain group names exactly (domain prefix
included), and then users are resolved dynamically at login. You create people
in AD once, and never touch the HMI project to onboard an operator. The failure
mode is equally characteristic — a typo in a group name silently produces a
user with no rights.

Siemens also invests in **badge login**: RFID/proximity card readers via
PM-LOGON on Comfort Panels and WinCC Unified, and fingerprint on some panels.
A badge tap is the login. This is not a gimmick — it is the only form of
per-operator identity that survives contact with cold, wet gloves and a
30-second shift handover, and it is directly relevant to a fish-processing
plant.

## 5. The MES layer

MES systems care less about *who may press this button* and more about *who
signed for this batch*.

- **Coarse privilege verbs.** Configuration-tab privileges commonly reduce to
  `Full` / `View` / `None` — administer, observe, nothing.
- **Signature flows.** Signature requirements are configured per process step
  and bound to roles, so the system can enforce "this step must be signed by
  someone holding the Quality role". Where a second signature is required, the
  system checks that the second signer actually holds the required role — and
  that they are a *different person* from the first. If users can approve their
  own work, dual verification is theatre.
- **21 CFR Part 11**, where it applies (pharma, food to a lesser degree),
  fixes the shape of the record: an electronic signature captures user ID,
  timestamp, and the **meaning** of the signature (approved / reviewed /
  verified), bound to the record. Non-biometric signatures need two distinct
  components — typically ID plus password. Audit trails must be
  computer-generated, tamper-evident, and capture who, what, when and — for
  changes — **why**.
- **Periodic access review.** Access is not set-and-forget: user and role
  assignments are re-reviewed on a schedule, dormant accounts removed,
  temporary admin grants time-boxed.

## 6. What everyone converged on

Stripping the branding away, the same eight decisions appear everywhere:

1. **Identity is delegated, with a local fallback.** AD, LDAP, OIDC — nobody
   wants a second user list. But every platform keeps a local break-glass
   account, because the domain controller *will* be unreachable at 03:00.
2. **Permission is a label on the object, not a list on the user.** Screens,
   objects and tags declare what they require; users carry what they hold. This
   scales; per-user ACLs do not.
3. **At least three planes: configure / administer / operate.** AVEVA makes it
   explicit (IDE / SMC / Runtime); Ignition arrives at the same place with
   separate tag-editing permissions; FactoryTalk splits Studio from Runtime
   Security. Nobody who has run this in production keeps a single admin bit.
4. **Anonymous read is the normal state.** Ignition grants `Public` to
   unauthenticated sessions by design. A wall display must show the line
   running with nobody logged in. Authentication gates *actions*, not *viewing*.
5. **Re-authenticate at the action, not just at the session.** Secured writes,
   verified writes, electronic signatures — the credential prompt sits on the
   dangerous write. This is what makes an unattended, always-on, logged-out
   panel safe.
6. **Four-eyes is a first-class primitive.** Verified writes and MES signature
   flows both encode "a second, different, suitably-roled person approved".
7. **Location is an authorisation input independent of identity.** Ignition
   Security Zones, FactoryTalk locational security. "Only from the panel at the
   machine" needs no user account.
8. **Every privileged action is audited with a reason.** Who, what, when, why,
   old value, new value — immutable.

And one anti-pattern, called out by name in more than one vendor's own
guidance: **shared generic accounts with auto-login**. Which is exactly what an
HMI degenerates into if login is too slow, which is why badge readers exist.

## 7. What this would mean for CentroidX

Mapping the above onto the code that exists today:

**The write choke point already exists.** Every operator write funnels through
`StateMan` behind `stateManProvider` (`lib/providers/state_man.dart`). A single
authorisation gate there covers every asset — buttons, setpoints, mode
switches — without touching the individual asset widgets. That is the highest
leverage single place to put this.

**Permission belongs on the asset config.** Assets are `*Config` classes with
`@JsonSerializable` + `build()` + `configure()`
(`lib/page_creator/assets/`). A nullable `requiredLevel` field on the common
config, surfaced as one dropdown in `configure()`, gives per-object
authorisation with the same shape the whole editor already uses — and
serialises into the existing page JSON for free. Null means "operate", the
default level, so nothing existing breaks.

**Three planes map cleanly onto three existing surfaces:**

| Plane | CentroidX surface |
|---|---|
| Operate | page view, side panes, asset writes |
| Configure | page editor, alarm editor, key repository |
| Administer | server config, IP settings, database config, system page |

The page editor is currently reachable by anyone; that is the gap that most
obviously wants closing first.

**Location is already modelled.** `localPreferencesProvider` is device-local by
design (see the SVN per-station database IP problem), so a station's zone —
"line panel" vs "office" vs "engineering laptop" — belongs there and cannot be
clobbered by a config sync from another station.

**Identity storage.** Users and role grants belong in the shared Postgres
alongside the rest of the config, which puts them under the existing
`PreferencesWatcher` LISTEN/NOTIFY machinery. Password hashes must *not* ride
the same sync path as ordinary preferences.

**Audit.** The collector/database layer already writes time-series to Postgres;
an append-only `audit` table with who / key / old / new / when / reason is a
small addition rather than new infrastructure.

**Login ergonomics.** For SVN specifically, keyboard login on a panel is a
non-starter — the numpad problems over VNC alone should settle that. A badge
tap or a 4-digit PIN on a touch numpad, with inactivity logoff back to an
anonymous read-only session, is the realistic shape. Note that "anonymous
read-only" is only coherent once anonymous *can* read, i.e. point 4 above.

## 8. Open questions

These need a decision before a design, and they are yours to make:

1. **Does SVN have an AD/LDAP the HMI could authenticate against**, or are these
   standalone machines? This decides whether we build a user directory or a
   thin adapter over an existing one.
2. **Is a regulatory audit trail in scope?** Food processing is not pharma, but
   customer audits and traceability requirements might still demand
   "who changed this setpoint" as a retained record. If yes, the audit table
   design changes (immutability, retention, export).
3. **Badge, PIN, or password?** This determines the whole login UX and whether
   we need hardware.
4. **Is four-eyes ever wanted here** — e.g. on freezer setpoints or on anything
   safety-adjacent — or is single-user authorisation enough?
5. **Where's the first cut?** The smallest genuinely useful slice is probably
   *lock the page editor and the config pages behind a PIN, leave operation
   entirely open*. That closes the accidental-damage hole without asking
   operators to change a single habit, and everything else can layer on later.
