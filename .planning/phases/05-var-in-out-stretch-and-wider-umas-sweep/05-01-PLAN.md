# Plan 5.1 — VAR_IN_OUT stretch + UMAS sweep

## Goal

Two parallel streams that share one merge gate:

- **A (FB-05).** A reachable VAR_IN_OUT member never disappears from
  the browser tree. Either the driver reads it via pointer
  dereferencing (path a), or it surfaces in the tree with
  `readable=false` + `unreadableReason="VAR_IN_OUT (PLC returns 0x94)"`
  (path b). NO silent omission either way.
- **B (SWEEP-01).** Surface 5-10 candidate UMAS edge cases beyond
  Bugs A & B. Triage each: accept into v1.1 with a new REQ-ID
  (SWEEP-02, SWEEP-03, …) or defer to v2.

## Decision tree for A

```
   read VAR_IN_OUT member through normal 0x22 path  ─► 0x94 returned
                       │
       ┌───────────────┴──────────────────────────────────────────┐
       ▼                                                          ▼
  pointer-deref feasible within timeline?            mark unreadable
       (need plc4j hint + live PLC                  ("not readable
        wire capture for IN_OUT pointer)             (VAR_IN_OUT)")
       │                                                          │
       ▼                                                          ▼
   path (a) — ship resolver + test                  path (b) — set
                                                    `readable=false` +
                                                    `unreadableReason`
```

Default to path (b) per Phase 5 acceptance criteria.

## Coexistence with Phases 2 & 3

Phase 2 owns the FB member expansion code that surfaces members in
the first place. Phase 3 layers VAR_INPUT / VAR_OUTPUT direction on
top. Both run in parallel in separate worktrees — neither has merged
into this worktree's base commit (`f9c6df19`).

This plan does NOT touch the Phase 2 expansion code path (it does
not exist here yet). Instead it adds the data-model pieces that
Phase 3 already plans to consume:

- `UmasFbMemberDirection` enum: `inputDir`, `outputDir`, `publicVar`,
  `inOut`
- `UmasVariableTreeNode.readable: bool` (default `true`)
- `UmasVariableTreeNode.unreadableReason: String?` (default `null`)
- `UmasVariableTreeNode.direction: UmasFbMemberDirection?` (default
  `null`)

A small helper file `umas_var_in_out.dart` defines the constants and
a single `classify(...)` function so Phase 2's expander can call into
it during member-list construction at merge time. Documented in
SUMMARY for the orchestrator.

## Accepted SWEEP candidates implemented in this plan

Decided during planning (see `05-SWEEP-TRIAGE.md`):

- **SWEEP-02** — Mask DB password in `DatabaseConfig.toString()`. Not
  UMAS but surfaced by sweep; deferred per scope discipline.
- **SWEEP-03** — UMAS error reporting consistency: include the
  sub-function name in every `UmasException.message` so log greps
  can tell paths apart. Cheap. **Accept v1.1.**
- **SWEEP-04** — `_handleSessionError()` does not clear
  `_projectCrc`. On PLC reboot, stale CRC can cause subsequent
  `readVariable` to succeed against a different project. **Accept
  v1.1.**
- **SWEEP-05** — `_maxWriteVariableRefs = 255` cap applied silently —
  caller can lose writes without notice. Add a warning log when the
  cap is hit so operators see it. **Accept v1.1.**

Deferred (logged with rationale):
- SWEEP candidates around MonitorPlc lifecycle under reboot,
  retry-queue saturation, type-variant handling (BYTE_STRING /
  WSTRING / multi-dim arrays) — see triage doc.
